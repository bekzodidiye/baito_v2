# 04 — SECURITY AUDIT: ADVERSARIAL RED TEAM ANALYSIS

## 1. OWASP API Top 10 Evaluation Matrix

| OWASP Category | Evaluation for Baito v3 | Risk Level | Mitigation & Verified Status |
| :--- | :--- | :--- | :--- |
| **API1: Broken Object Level Authorization (BOLA/IDOR)** | Analyzed all `/jobs`, `/applications`, `/payments/cards`, `/chats` endpoints. | **Low** (Protected) | Card CRUD explicitly checks `PaymentCard.userId.in_(user_ids)`. Chat messaging verifies that `current_user.id` is a participant in `Chat.workerId` or `Chat.employerId`. Media viewing verifies ownership before serving S3 objects. |
| **API2: Broken Authentication** | Session management, JWT decoding, SMS verification. | **Low** (Protected) | Registration requires valid verification grant generated by `/auth/verify-sms`. Session tokens are validated against `ActiveSession` with idle revocation window (`is_live`). Passwords hashed with BCrypt. Password changes revoke all other active sessions. |
| **API3: Broken Object Property Level Auth** | User profile updates, user registration role assignment. | **Low** (Protected) | Public registration endpoint (`/users/open`) hard-codes role assignment to either `"worker"` or `"employer"`; caller cannot pass `role: "admin"`. Sensitive fields like `isVerified`, `isBanned`, `balance` are stripped during regular updates. |
| **API4: Unrestricted Resource Consumption** | SlowAPI rate limiting, image upload size, WebSocket floods. | **Low** (Protected) | Endpoints are protected by SlowAPI (`@limiter.limit`): `/auth/login` (10/min), `/payments/withdraw` (5/hour), `/payments/cards` (10/min). Chat WebSockets enforce 20 msgs / 10s flood control and disconnect abusive sockets. |
| **API5: Broken Function Level Authorization (BFLA)** | Administrative endpoints under `/api/v1/admin/*`. | **Low** (Protected) | All admin routers enforce `Depends(get_admin_user)` which strictly validates `current_user.role == 'admin'`. Non-admin requests immediately return HTTP 403 Forbidden. |
| **API6: Unrestricted Access to Sensitive Business Flows** | Shift start, day settlement, withdrawal requests. | **Low** (Protected) | Worker shift start stamps exact arrival time. Finishing shifts enforces that only dates that have arrived can be settled. Withdrawal requests enforce `Idempotency-Key` and atomic balance debiting. |
| **API7: Server Side Request Forgery (SSRF)** | S3 media uploads, Soliq tax integrations, Eskiz SMS. | **Low** (Protected) | Media endpoints do not accept arbitrary URLs for server-side fetching. Media uploads go directly to S3 via pre-signed structures; downloads use strict alphanumeric regex (`OBJECT_KEY_RE`). |
| **API8: Security Misconfiguration** | Sentry DSN parsing, CORS headers, error disclosures. | **Low** (Protected) | Sentry DSN initialization is wrapped in safe exception handlers (`test_a_malformed_sentry_dsn_cannot_take_the_app_down`). Generic error messages are translated; internal database tracebacks are hidden in production mode. |
| **API9: Improper Inventory Management** | API versioning, obsolete endpoints. | **Low** (Protected) | All active endpoints are organized under `/api/v1`. Deprecated endpoints (like Uzum merchant stubs) were cleanly purged in migration `f1263e379685_schema_fixes_and_uzum_removal`. |
| **API10: Unsafe Consumption of APIs** | Eskiz SMS gateway, external payment webhooks. | **Low** (Protected) | SMS dispatch is queued asynchronously in Celery with strict timeouts (10s connect, 5s read). Webhook inputs are validated via HMAC signature before mutating any ledger state. |

## 3. Cryptographic Verification & Secret Handling

1. **SECRET_KEY Verification**:
   - Used for JWT signing and HMAC-SHA-256 map cache envelopes.
   - Tested: `map_cache.py` rejects empty or hard-coded default fallback keys when running in production environment.
2. **Timing Attack Protection**:
   - Signature checks in `map_cache.py` and `invoice_link.py` utilize `hmac.compare_digest()` to ensure constant-time comparison, preventing timing-channel side-leak attacks.
3. **PII and Data Protection**:
   - Passports, personal identification numbers (JSHSHIR), and selfie verification photos are isolated in S3 with strict database-backed ownership guards (`_is_identity_document`).
   - Phone numbers of hired workers are never revealed to anonymous scrapers or unhired employers (`test_hired_worker_phone_is_never_exposed_to_employer`).
